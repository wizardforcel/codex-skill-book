# 知识库建设与检索优化规则

本文件吸收第二轮知识库建设建议，目标是让人和 AI 都能少扫描、快定位、可追溯。

## 1. 吸收为硬规则

```text
层次分明：内容必须进入明确区域和层级。
入口统一：新内容先进入同一个入库系统，再按规则分流。
原子化：一个正式条目只承载一个可复用观点、方法、事实或动作。
元数据前置：分类、状态、可信度、来源、摘要写在 frontmatter。
正文写内容：正文只写解释、判断、过程、证据和为什么。
先导航后内容：先读规则和导航，再读索引，最后打开具体文件。
定期复核：正式条目必须有 last_reviewed；事实性或易过期内容补 last_verified / valid_until。
写给三个月后的自己：每条正式内容要说明“为什么记录”和“何时使用”。
```

## 2. 本库化吸收

有些建议要吸收精神，但不照搬形式。

```text
用问题命名：
  方法、判断、思辨卡片优先用“如何做 X”“为什么 X”“X 是否成立”。
  项目、日志、索引、来源材料保留对象名或日期，不强行改成问题。

建 _nav.md：
  本库已有 00_索引、00_思辨MOC 和区域索引，不额外引入 _nav.md。
  新区域需要 AI 地图时，统一命名为 00_区域索引.md 或放入 00_MOC。

项目 status：
  通用 status 已用于入库状态，不用 active/done 覆盖。
  项目进度统一写 project_status: active / done / paused / abandoned。

思辨文件末尾加核心观点：
  固定“## 核心观点”标题必须吸收。
  但 AI 检索更依赖 frontmatter 和正文前段，因此 summary 和核心观点应靠前；长原文前或提炼区内必须有核心观点，不只藏在末尾。
```

## 3. 不作为硬规则

```text
所有文件都改成问题标题：会损害项目、日志、索引、来源文件的可读性。
所有区域都新建 _nav.md：会和现有索引/MOC 重复。
所有内容都加 valid_until：稳定思想、个人复盘、历史日志不一定需要有效期。
Inbox 完全不可读：Inbox 可用于整理任务，但不能作为正式知识依据或向量索引来源。
```

## 4. 缺少并补入的规则

```text
summary：所有正式可调用文件必须有一句话摘要，AI 先读摘要判断是否打开全文。
aliases / keywords：标题不够覆盖常见问法时，用别名和关键词补检索入口。
last_verified：事实性、工具性、职业/政策/技术内容需要最近验证日期。
valid_until：高时效内容需要有效期，到期后默认降级为待复核。
source_quality：外部资料可标注 primary / secondary / self_note / ai_generated。
conflict_policy：发现旧结论和新结论冲突时，不直接覆盖，先在 conflict_note 字段写冲突说明和来源差异。
index_maintenance：新增正式条目后，必要时更新对应索引/MOC。
```

## 5. 推荐 frontmatter 字段

正式可调用文件优先具备：

```yaml
type:
status:
truth_status:
area:
summary:
source:
source_quality:
related:
usable_for:
aliases:
keywords:
route_target:    # 仅人工辅助模式使用
route_reason:    # 仅人工辅助模式使用
confidence:
last_reviewed:
last_verified:
valid_until:
conflict_note:
tags:
```

项目文件额外使用：

```yaml
project_status: active | done | paused | abandoned
```

思辨原始记录额外使用：

```yaml
extract_status: pending | done
extract_depth: file_level | content_level
```

## 6. AI 检索顺序

AI 回答或调用知识库时，按以下顺序缩小范围：

```text
1. 读 00_规则/00_AI工作入口.md。
2. 判断任务类型和目标区域。
3. 读对应区域规则。
4. 需要混合检索时读 00_规则/18_混合检索与向量索引规则.md。
5. 读区域索引/MOC/Bases，先找候选路径。
6. 按路径、type、status、truth_status、project_status 过滤。
7. 先读标题、summary、aliases、keywords、## 核心观点。
8. 必要时用 10_正式库/00_检索索引 做 BM25 + 向量辅助召回。
9. 只打开候选文件正文。
10. 必要时追溯 source。
11. 回答时说明可信边界或过期风险。
```

禁止直接全文扫描正式库来碰运气。

## 7. 向量索引排除规则

若后续使用向量索引或 AI 自动检索，默认排除：

```text
10_正式库/00_检索索引
10_正式库/02_思辨区_待整理
10_正式库/02_思辨区/01_思辨记录
10_正式库/02_思辨区/05_Inbox
10_正式库/02_思辨区/06_Archive
01_导入原始材料
02_入库处理区
99_垃圾区
05_Inbox
旧候选记录
type: inbox
status: raw
status: ai_generated 且未人工允许
truth_status: unverified
truth_status: discarded
#入库/待确认
#入库/拒绝
#归类/待归类
```

这些内容可以作为整理材料或来源追溯，但不能直接进入正式回答依据。

混合检索的索引范围、切块、角色权重和重建规则以：

```text
00_规则/18_混合检索与向量索引规则.md
```

为准。

## 8. 原子化边界

```text
观点卡片：一个文件只写一个核心观点。
方法卡片：一个文件只解决一个具体问题。
事实参考：一个文件只承载一个主题范围。
项目主页：允许承载项目总览，但要把具体经验拆成独立卡片。
日志：允许按日期聚合，不要求原子化。
索引/MOC：允许聚合链接，但不写新结论。
```

如果一个文件自然长出多个可复用观点，后续应拆成多个卡片并互相链接。
