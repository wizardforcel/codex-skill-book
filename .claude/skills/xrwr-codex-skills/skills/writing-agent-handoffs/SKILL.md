# 作業依頼の引き継ぎ

相手が自分の環境で作業を完了し、依頼元が結果を確認できるよう、ユーザーがそのまま貼れる依頼文を作る。相手がエージェントでも、コピー後の権限・実行先・成果物の共有は自動で引き継がれると仮定しない。

## 依頼文を作る

- ユーザーが指定した目的、対象と比較元、固定すべき条件、実行環境、変更してよい範囲を、相手が実行できる具体さで書く。実物のリンク・バージョン・設定を確認し、未検証の動作や数値を事実として書かない。
- 必要な入力・モデル・コード・依存資産とアクセス範囲を明記する。非公開資産をコピーして相手が実行する場合は、**コピー先や結果・ログにも、依頼元が読める指定グループまたはユーザーの権限を付けること**を依頼文に含める。元の資産の共有とコピー先の共有は別に扱う。公開を求めず、既定で非公開を維持する。グループ名やロールはユーザーの指定と実際の権限に従う。
- 実行後は、実行先URL、固定バージョンまたはrun ID、状態、成果物とログの取得先を報告してもらう。依頼元が継続監視する場合は、共有後にその実行先の読み取り・ログ取得が可能であることも確認対象にする。
- 停止・時間・予算・失敗時の条件と、その起点を明記する。性能評価では必要な計測対象、時間軸、集計窓、比較元、グラフ、欠測の扱いを指定する。途中停止で成果物が失われる可能性があれば、実行中のログ回収方法も依頼に含める。プロジェクト固有の停止ルール・GPU投入前検査に従う。
- 依頼文に含めるのは、目的達成に必要な操作だけにする。比較条件や閾値を発明せず、未確定な点は明確にする。テキスト作成や共有準備だけでは、相手への送信、GPU実行、再試行、公開などの許可にはならない。

## 実行の確認と監視

- 相手が別の会話・サービスのエージェントである場合、自分が直接連絡できると仮定しない。ユーザーが転送する依頼文に、必要な条件を最初から含める。事後に依頼の追加が必要になった場合は、自分で実行可能な手段とユーザーへの依頼を区別して説明する。外部への送信は明示的な許可があるときだけ行う。
- 返ってきたURLと固定バージョンを照合し、状態、実行ログ、成果物それぞれを利用可能な経路で確認する。**メタデータ・状態・ログ・成果物は別のAPIや権限の場合がある。** 一つの経路の403・404だけで全経路へのアクセス不能や権限不足と断定しない。安全な別経路を試し、どの操作が成功・失敗したかを具体的に伝える。
- 監視を依頼されたら、固定実行を指定してログ・状態を継続的に回収できることを確認する。実行先が未確定なら、確実に特定できる対象を監視し、非公開の別名コピーを検出できない可能性を伝える。停止条件の自動処理は権限・対象・実ログの確認を伴い、監視開始や接続だけを実行ログと誤認しない。
- 相手の報告と自分で検証できた事実を区別する。依頼文から共有や確認が漏れた場合は、誤りと実際の影響を明示し、自分でできる復旧を先に試す。
