# Making Slides

理解の負債を減らすための資料を、1枚1メッセージの16:9スライドで作る。読み手は全部を精読しない。見出しの一文と図だけで要点が伝わり、細部は必要なときに開けるようにする。

## 形式

- Claude Docs のドキュメントを1つ作り、スライド1枚を1つの図（widget）として埋め込んで並べる。1枚＝`viewBox='0 0 960 540'` のSVG。コメントや文字の直接編集ができ、スマホでも読める。
- ドキュメントにはスライドだけを並べ、スライドの間に説明文の段落を置かない（2026-11-16 ユーザー指定）。出典・推測や未検証の明示はスライド内の小さな文字にし、出典の一覧と「実物で見られる箇所」は最後の1枚にまとめる。
- Claude Docs のコネクタがない環境（Codexなど）では、同じSVGを縦に並べた1枚のHTMLにする（`writing-phone-docs` の見た目に従う）。
- Docs の作り方・制約（文字ごとの `data-claude-text-id`、ループ内で文字を作らない、`<use>`・`<style>`・`<foreignObject>` 不可など）は Docs の `guide` の `topic.diagram` に従う。このスキルはその上での見た目と構成を決める。

## 構成

1. 書く前に、読み手が読後に分かっていること（1文）と、枚数（通常5〜8枚）を決める。
2. 1枚目は表紙、早いうちに全体像、最後に「どうするか」（次の手・推奨）を置く。間の枚数と順番は内容で決める。
3. 各スライドの見出しは**結論の一文**にする（「前処理：欠損を中央値で埋めると CV が 0.01 上がる」）。話題名だけの見出しにしない。
4. 1枚に載せる主張は1つ。要点や結果の数字を添えるのは、図だけでは伝わらないときだけにする。毎枚同じ位置に要点帯を置かない。
5. 強調は1枚に1か所だけ赤にする。数字・名前・条件は元の資料にあるものだけを書き、推測で埋めない。自己申告や未検証の値はそう書く。
6. 理解のための資料なので、箱を名前だけにしない。読み手が「この箱の中は？」「何回？」「どれくらい？」と聞かずに済むところまで、数値・形・設定を書き込む。発表用のゆったりした密度より、1枚の情報量を優先してよい。

## 1枚ごとの描き方を決める

**型を選んでから中身を流し込まない。** 1枚ずつ、コードを書く前に次の4行を作業メモに書き、それから描く。

1. 主張：見出しの一文
2. 内容の形：その主張を支えるものが、どんな形をしているか（下の表の左列）
3. 描き方：その形がひと目で分かる描き方（下の表の右列。合うものがなければ新しく考える）
4. 箇条書きにしない理由：箇条書きだと読み手が頭の中で何を組み立て直すことになるか

| 内容の形 | 描き方の例 |
| --- | --- |
| 複数のモジュールからなる全体像 | 実際の分岐と合流のとおりにカードを置き、各カードに操作の小さな絵・平易な一言・モデルや設定・詳細ページ番号（「モデルのアーキテクチャを描くとき」） |
| 順序のある処理 | 番号付きの箱を矢印でつなぐ。段数が多ければ折り返す。各箱に何をするかと数値を2行 |
| 時間・締切・期間 | 時間軸を引き、期間は帯、締切は菱形、上限は縦の点線 |
| 量の違い・規模 | 比率どおりの長さの棒。差の大きさそのものを見せる |
| 入れ子の構造（モデル・モジュール） | 枠を横に並べ、全体 → 繰り返しブロックの中身（×回数）→ 周辺と掘り下げる。テンソルの形・層の設定を書く |
| 注目するモジュールでのデータの形の変化 | 格子・マス目の列・層の板で、形が変わる様子を左から右へ描く（「モデルのアーキテクチャを描くとき」） |
| 操作で数値がどう変わるか | 操作前と操作後の表（行列）を並べ、間に操作の手順とループを置く |
| 空間・分布の変化 | 点の散らばりの前後を並べる（模式図と明記） |
| 組み合わせ・制約 | 具体的な1例をチップや表で示し、数え上げの数を添える |
| 複数の設定・案の比較 | 行が設定、列が条件と結果の表。採用するものだけ赤 |
| 計算式の連なり | 段ごとに式を書き、右に意味と使わない条件を添える |
| 構成比・重み | 比率どおりの棒やピル。最大のものだけ強調 |
| 2つの実物の違い | 実物の抜粋を2列に並べ、共通点・違いを示す |
| 種類ごとの注意・リスク | 種類を色付きのタグにして、行ごとに中身と関係する頁 |

連続する2枚が同じ配置になったら、内容の形が本当に同じかを見直す。同じ箱の並びに収めるために内容を削ったり、別の形の内容を箱に押し込んだりしない。

### 処理の流れの全体像を描くとき

守ることは2つ。描き方（箱・木・注釈つきの例など）は内容に合わせて決める。

- **全体を描いたうえで、大事なところを強調する。** 先にその手法の核心がどこかを決める。全段を省かずに描き、核心は大きく・強い色で目立たせ、下ごしらえや後処理は小さく控えめにする。全段を同じ大きさで並べると、どこが重要か分からない。
- **入出力を明示する。** 具体的な入力（例題の1件など）から始め、各段が何を受け取り何を出すかを実際の値で書き、最後の出力までつなげる。操作の名前だけを並べない。

### 分かりにくい仕組みを掘り下げるとき

読み手が知らない手法（Sinkhorn、グループ中心化など）は、1枚に詰めず「なぜ必要か → どう動くか → このコードではどう使っているか」の2〜3枚に分ける。動きは小さな例（6件・3クラス程度）で見せ、その数値は**対象のコードと同じ計算を実際に実行して**出す。例が架空なら「説明用の例（数値は架空）」と明記する。掘り下げ版のデッキは20枚前後になってよい。

### モデルのアーキテクチャを描くとき

全体と注目する部分で描き方を分ける。全体をテンソルの形で描くと情報が多すぎて読めない。

- **全体**：読み手が知らない手法があっても「ここで何をしているか」が分かって読み飛ばせるようにする。仕組みは詳細のページに任せる。
  - 配置は実際の構造どおりにする。並列に動く部分は縦に並べて分岐・合流を線で描き、横から情報を渡すもの（グループ化など）は点線でつなぐ。一列に並べて構造を隠さない。
  - 各モジュールはカードにして、①操作を表す小さな絵（詳細ページと同じ絵）、②名前と何をしているかの平易な一言（「確率を平均し、偏りをならす」）、③使っているモデル・設定を1〜2行（「ResNet-50 を fp16、最後の2段だけ学習」）、④詳細ページの番号、を載せる。絵と一言だけでは情報が足りない。
  - 混ぜる割合や上限のような設計値は書いてよい。どれが効いたかという結果の話は入れない。
  - 本筋でない準備などは注記に回す。
- **注目する部分**（そのデッキで理解してほしい1〜2か所）：テンソルの形の変化をそのまま絵にする。ベクトルはマス目の列、行列は格子、層は板の重なりで描き、平均・連結・射影で形が変わる様子を見せる（Jay Alammar の「The Illustrated Transformer」の描き方）。使う層だけ色を付ける、捨てるトークンを灰色にする、など「何を選び何を捨てるか」を図で見せる。棒の高さなどが模式なら明記する。
- 部品は `assets/tensor-helpers.jsx` の `grid`・`vec`・`slabs`・`segs`・`bars` を使う。
- どの部分を詳しく描くかは、見出しの主張に直接かかわるところで選ぶ。全部の部品を同じ細かさで描かない。

各部品では、入力の形・処理・出力の形・なぜその設計か・重さ（パラメータ数や時間）・出典（ファイルやセル）が分かるようにする。原典（writeup・論文）に分かりやすい図があれば、描き直さず出典付きで使う。

### 実物スライドを選ぶ基準

実物の抜粋は効くが手間がかかるので、絞って作る。

1. 対象は、見出しが「〜を変えた／書き換えた／圧縮した／見分けにくい」などで、その中身が文章・トレース・プロンプト・データ1件・コードのもの。見出しと数字で伝わるもの（構成比、結果）は対象外。
2. その中から、効果が最も大きいか、全体の理解の鍵になるものを **1デッキに1〜2枚まで**。
3. リポジトリ・データ・ログにある実物から抜き出せるときだけ作る。作った例や要約で代用しない。抜粋は各列8行程度まで、全文が短ければ全文。
4. 選ばなかった候補は、デッキ末尾の「実物で見られる箇所」の表に1行ずつ（箇所・見せられるもの・必要なもの）並べる。読み手が「これ見せて」と言ったら1枚足す。

## 見た目と部品

- 色・文字サイズ・配置・部品の寸法は [references/style.md](references/style.md) に従う。
- アイコンは手で描かず、同梱の Lucide（ISC）から使う。名前を探して、JSXの関数を生成して貼る:

```bash
python3 -I <skill-dir>/scripts/icons.py search idea          # 名前とタグで検索
python3 -I <skill-dir>/scripts/icons.py jsx lightbulb trophy  # 関数を出力
```

  出力された `const iLightbulb = (x, y, s, c, f = 'none') => …;` を `export default` の前に置き、`{iLightbulb(60, 436, 40, MB)}` のように呼ぶ。(x, y) は左上、s は大きさ、c は線の色、f は塗り。
- `assets/examples/` は色・部品の寸法・文字の大きさ・SVGの書き方の見本（文字はダミー）。**配置は写さない。** 配置は「1枚ごとの描き方を決める」で決める。
- `~/.local/share/agent-skills-private/making-slides/` があれば、実際のデッキの非公開の実例と、その一覧（README.md）がある。描き方の幅を知る参考にだけ使い、公開リポジトリには入れない。
- アイコンの `<g transform>` の書き方は Docs の検査を通ることを確認済み（2026-11-16）。固定色について `typed_colour`（ダークモードで色が変わらない）の警告が出るが、スライドは白背景を自分で描くので想定どおりとして扱う。

## 確認

- 1枚書いたら Docs の `read`（`payload: {"kind": "screenshot"}`）で描画を見て、文字のはみ出し・重なり・枠からの切れを直す。全枚数を書いてからまとめて直さない。
- 英文の抜粋は折り返されないので、14px で1行50文字程度に自分で区切る。
- 最後に、見出しだけを順に読んで話がつながるかを確かめる。

## 全体像スライドを保つとき

コンペやプロジェクトの「全体像」スライドは、新しい版を足さず同じドキュメントを書き換える。詳細な解説資料を作ったら、全体像のどの項目に関わるかを確認し、変わった箇所だけを直して詳細資料へのリンクを添える。
