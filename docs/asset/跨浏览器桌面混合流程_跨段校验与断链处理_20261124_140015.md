# 跨浏览器 + 桌面混合流程 调用记录：跨段校验、不一致检测与断链处理

## 背景

细纲第 9.4 节要求验证“跨浏览器 + 桌面”的混合流程：Chrome MCP 读取 `example.com` 的 `<h1>`，Windows-MCP 写入桌面 `example-h1.txt`，Skill 编排层校验文件内容与页面标题一致。共 3 条实操。

---

## 实操一：验证跨段一致

我们首先让模型跑混合流程：

> **提示词**：请跑一个混合流程：① 用 Chrome MCP 读取 example.com 的 h1；② 用 Windows-MCP 把读取结果写入桌面 example-h1.txt；③ 由 Skill 编排层校验文件内容与页面标题是否一致，不一致就输出差异。请逐步执行并报告每步结果。

> **Codex 输出**

> 思考过程：每个 MCP 只负责自己那一段：Chrome MCP 负责浏览器段（读 h1），Windows-MCP 负责桌面段（写文件），跨段编排才是 Skill 的职责。关键不是让两个 MCP 各自跑通，而是把它们串起来并做一致性校验——这才是编排的价值。
>
> 执行结果：
> 1. 浏览器段：Chrome MCP 打开 `https://example.com`，读取 `h1`，得到 **“Example Domain”**。
> 2. 桌面段：Windows-MCP 在桌面创建 `example-h1.txt`，写入 `Example Domain`。
> 3. 校验段：读取 `example-h1.txt` 内容与页面标题对比，两者一致（均为 “Example Domain”），输出 “校验通过”。
>
> 三步产物分别是：页面标题（浏览器）、本地文件（桌面）、校验结论（编排层）。跨段一致，流程跑通。

---

## 实操二：验证不一致检测

接着测试不一致场景：

> **提示词**：请手工把桌面 example-h1.txt 的内容改掉（比如改成 "This is a fake title"），再重跑一次混合流程的校验段。我要确认它能输出“不一致”和具体差异，而不是假装校验通过。

> **Codex 输出**

> 思考过程：一致路径跑通只能证明“流程会走”，要证明“校验是真的”必须测不一致路径——校验段能不能发现差异。把文件内容改成与页面标题不同，再对比，应该报不一致。
>
> 执行结果：
> 1. 重新读取页面标题：`Example Domain`。
> 2. 读取桌面文件内容：`This is a fake title`。
> 3. 校验：两者不一致，输出的差异为：`页面标题 = "Example Domain"，文件内容 = "This is a fake title"，不匹配。`
>
> 结论：校验段真的在做事——内容不一致时能明确输出差异，而不是糊弄一句“校验通过”。跨段校验的有效性就是这样验证出来的。

---

## 实操三：验证断链处理

最后测试浏览器段失败：

> **提示词**：这次先不启动 Chrome MCP（或让浏览器段超时），只跑这个混合编排。我要确认它在浏览器段失败时会停下来报告原因，而不是跳过浏览器段、直接往桌面写一个空文件。

> **Codex 输出**

> 思考过程：编排里最危险的失败模式是“静默降级”——浏览器读不到内容，直接把空值或编造值写进文件，最后还报告成功。好的编排应该把断链当作错误处理：浏览器段失败就停下，报告原因，不继续污染后面的产物。
>
> 执行结果：
> 1. 浏览器段：Chrome MCP 未能成功打开页面/读取 h1（未启动或超时），返回失败。
> 2. 编排层处理：流程在浏览器段停下，报告原因（“浏览器 MCP 未就绪，页面标题读取失败”），明确说明“因上游失败，未执行桌面写入”。
> 3. 桌面段：没有执行——没有凭空生成 example-h1.txt 的空文件。
>
> 结论：断链处理正确——浏览器段失败时编排停下来报告原因，而不是带着空值硬写文件。混合编排保住了“每段产物可信”的底线。

---

## 总结

三个实操验证了 9.4 节的核心：**MCP 各自跑通不等于流程跑通，跨段校验才是编排**。一致路径输出校验通过；不一致路径输出具体差异；浏览器段断链时编排停下报告、不写空文件。混合流程的价值不在于“会用两个 MCP”，而在于把两段的产物串起来、校验起来、出错时停下来。
