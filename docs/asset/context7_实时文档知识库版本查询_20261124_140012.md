# context7 调用记录：实时文档版本查询与来源验证

## 背景

细纲第 6.4 节要求使用 `context7`（MCP 单独跑通）为 AI Agent 提供实时、版本精确的文档：查询本地项目所用库的当前版本文档并给出来源，验证版本精确性、同问不同答、来源真实性。共 3 条实操。

---

## 实操一：验证版本精确性

我们首先让模型查询当前版本文档：

> **提示词**：请用 context7 查询 React 的当前版本文档。我要你回答里同时给出库版本、文档来源/链接、关键 API 用法。然后再对比一下：如果不用 context7、直接凭印象回答，可能是什么样？

> **Codex 输出**

> 思考过程：模型训练数据里的记忆是有截止点的，回答框架/库用法时容易用旧版写法。context7 的定位就是按需拉取当前版本文档，解决“训练数据滞后”的问题。所以这一步的核心不是“会写 React”，而是“给到的是哪个版本的用法、有没有出处”。
>
> 使用 context7 查询的结果：
>
> - 库版本：react 19.x（当前稳定版）
> - 文档来源：https://react.dev/learn / https://react.dev/reference/react
> - 关键 API 用法（与旧版的关键差异点）：
>   - 函数组件与 Hooks（useState、useEffect）是当前推荐用法，旧的 class 组件写法仍是旧文档；
>   - 若问的是某个具体 API（如 createRoot），context7 会返回符合当前版本的签名和示例。
>
> 与“不查文档凭印象回答”的对比：凭印象可能给出旧版写法（例如还在用 ReactDOM.render），context7 版本精确的答案会纠正这一点。把文档来源链接写入 6.1 的 vault 笔记后，“外部文档知识库 → 个人知识库”的回证链路成立——笔记里有链接可回查。

---

## 实操二：验证同问不同答

接着验证版本敏感：

> **提示词**：我在一个装旧版 React（比如 17）的项目里问你 hooks 的用法，再在一个装 React 19 的项目里问你同一个问题。请比较两次回答是否因版本不同而不同。我要确认 context7 不是固定一套文案。

> **Codex 输出**

> 思考过程：context7 是高阶工具，查询结果应反映“目标版本”而不是一套固定文案。做法是：在两次查询里显式限定版本号（或让 context7 读取项目依赖），对比返回的 API 写法。
>
> 对比结果：
> - 版本 17 的场景：返回的示例使用 `ReactDOM.render(<App/>, root)` 之类旧入口写法，并标注该写法对应 17 的文档。
> - 版本 19 的场景：返回 `createRoot(...).render(...)` 新入口写法，以及 19 才有的新能力。
>
> 结论：同一个问题，context7 按版本返回不同内容，且都标注来源。它不是“固定一套文案换个版本号”，而是真的按版本差异给不同写法。

---

## 实操三：验证来源真实性

最后验证链接真实：

> **提示词**：把 context7 返回的文档链接原样保留在回答里，不要丢。然后请手工打开其中 1—2 个链接，确认链接真实可达、内容支持回答中的说法，防止它返回“看似权威的编造链接”。

> **Codex 输出**

> 思考过程：LLM 有“编造链接”的风险——看起来像官方文档的 URL，实际打不开或不存在。验证办法是原样保留链接并用浏览器/HTTP 实际访问一次。
>
> 验证结果：
> - context7 返回的链接（例如 https://react.dev/reference/react/createRoot）原样保留，未改写。
> - 打开该链接：页面真实可访问，标题为 CreateRoot，内容与回答中的 API 示例一致，说明来源真实、内容支撑说法。
>
> 结论：context7 的来源环节可验证——链接可达、内容对得上，不是编造的“权威链接”。这也是 6.3 节“回答必须能追溯到原文”在外部文档上的体现。

---

## 总结

三个实操验证了 6.4 节的核心：context7 解决训练数据滞后——给库版本 + 文档来源 + 关键 API，且能纠正旧版写法；同一问题按版本不同返回不同写法；返回链接真实可达、内容支撑回答。它与第 6 章的 vault 形成分工：Vault 管个人知识，context7 管外部技术文档，两者都要求答案可追溯。
