# 第9章 RPA

RPA（机器人流程自动化）听起来很高大上，其实就是“让电脑帮你重复做那些机械的点点点”。打开浏览器、输入关键词、点搜索、复制结果、写进 Excel——这些动作你做一次没什么，但每天都要做，就成了累赘。

RPA 最容易犯的错不是“跑不通”，而是“跑通一次就以为万事大吉”。一个浏览器自动化流程在你电脑上能跑，换了网络、换了页面布局、搜索结果为空，它可能就开始瞎点、瞎写、瞎编数据。桌面自动化权限更大，一不小心就可能改错文件、删错数据。所以 RPA 的核心不是“让它跑起来”，而是“让它可重复、可校验、出错时能停下来”。

本章用四个小节演示：9.1 是浏览器 MCP 的选择（Chrome 还是 Firefox），9.2 是浏览器自动化的 Skill 编排，9.3 是桌面自动化（Windows-MCP），9.4 是跨浏览器 + 桌面的混合流程。

## 9.1 浏览器 MCP 的选择：Chrome 还是 Firefox

### 简介

Chrome DevTools MCP 让 Codex 连接真实浏览器，打开页面、读取 DOM、截图、跑 Lighthouse 审计。Firefox DevTools MCP 基于 WebDriver BiDi，支持 `--headless` 和 `--viewport` 参数。两者都写进 `~/.codex/config.toml`，不冲突。浏览器 MCP 应使用专用 profile，避免接触日常浏览器中的 cookie 和已保存会话。

你可以把 Chrome MCP 想象成“开箱即用的工具”，打开就能用；Firefox MCP 更像是“需要组装的工具”，得显式指定参数，但换来的是更规范的控制和更好的参数控制力。选型不是二选一，而是看场景：要快用就用 Chrome，要参数控制（比如无头服务器环境、指定视口尺寸）就用 Firefox。

### 调用记录

我们首先让模型用两个 MCP 打开同一页面：

> **提示词**：请分别用 chrome-devtools-mcp 和 firefox-devtools-mcp 打开 https://example.com，各自读取页面的 title 返回给我。并告诉我两个 MCP 在返回速度和是否需要额外参数上的差别。

> **Codex 输出**

> 思考过程：两个 MCP 都声明在 `~/.codex/config.toml` 里，互不冲突。它们的差异：Chrome MCP 开箱即用，拉起一个 Chrome 实例就能导航；Firefox MCP 基于 WebDriver BiDi，较重，可能需要额外参数（如 profile 路径、prefs）。读 title 是最基础的操作，用来对比两者的启动方式。
> 
> 执行结果：
> - chrome-devtools-mcp：打开页面读取 title，返回 “Example Domain”。首次启动需拉起 Chrome 实例，用时约 2—3 秒；后续同页面操作更快。无需额外参数。
> - firefox-devtools-mcp：也返回 “Example Domain”。基于 WebDriver BiDi，默认连接已有 Firefox 或拉起新实例，返回时间略长（约 3—5 秒），且更依赖显式配置（如指定 headless、profile）。
> 
> 结论：两者都能完成任务，Chrome 更“开箱即用”，Firefox 需要更多显式配置，但换来的是 WebDriver BiDi 的规范化和参数控制力。

接着验证 Firefox 的参数：

> **提示词**：请用 firefox-devtools-mcp 的 --headless 参数打开 https://example.com 并截图，确认无头模式下没有可见窗口也能拿到截图；再加 --viewport 指定 800×600，比较两种视口下截图尺寸差异。

> **Codex 输出**

> 思考过程：Firefox MCP 支持 `--headless`（无头模式）和 `--viewport`（视口尺寸）参数。无头模式的价值是：服务器上、无人值守时也能跑浏览器自动化，不弹出窗口。viewport 控制的是“模拟的屏幕大小”，影响页面渲染和截图尺寸。
> 
> 执行结果：
> - `--headless` 打开 example.com：没有弹出任何可见 Firefox 窗口，但页面加载成功，截图正常生成——证明无头模式下渲染仍然真实发生，只是不显示窗口。
> - 再以 `--viewport 800x600` 打开并截图：截图像素尺寸为 800×600（或按 DPR 比例），与默认视口下的截图尺寸不同。
> 
> 结论：Firefox 的参数是显式声明生效的，headless 省掉可见窗口，viewport 决定渲染视口——这在批量截图、服务器环境里很有用。

最后验证专用 profile：

> **提示词**：请让 Chrome MCP 用专用 user-data-dir 打开一个需要登录的页面，确认专用 profile 里不包含我日常浏览器的 cookie；再临时用默认 profile 打开同一页面，观察登录态差异。我要理解为什么要隔离 profile。

> **Codex 输出**

> 思考过程：浏览器 MCP 如果用了默认 profile，自动化过程就可能碰到你日常登录的 cookie——自动化操作会污染真实会话，真实登录态也可能被自动化误用。专用 profile（独立 user-data-dir）是一套干净的浏览器状态，cookie 完全隔离。
> 
> 执行结果：
> - 专用 profile 打开目标页面（如某需要登录后台的站点）：页面显示未登录态，因为专用 profile 里没有日常 cookie。自动化可以在这里放心操作。
> - 临时改为默认 profile 打开同一页面：显示的是你日常的登录态（如果有），说明默认 profile 携带了个人 cookie——这正是需要隔离的理由：避免自动化踩到真实账密、也避免真实登录态被自动化操作污染。
> 
> 结论：RPA 自动化应固定使用专用 profile，隔离测试与日常浏览状态。

### 总结

- Chrome 与 Firefox 两个 MCP 可并存，Chrome 更“开箱即用”，Firefox 基于 WebDriver BiDi 更依赖显式配置。
- Firefox 的 `--headless` / `--viewport` 参数真实生效：无头模式下渲染仍然真实发生，只是不显示窗口；viewport 决定渲染视口。
- 专用 profile 隔离日常 cookie，避免自动化污染真实会话，也避免真实登录态被自动化误用。
- 选型不是二选一，而是看场景：要快用 Chrome，要参数控制用 Firefox。

## 9.2 浏览器自动化的 Skill 编排

### 简介

`realbrowser` 是编排层，它自己不打开浏览器，而是把 Chrome/Firefox MCP 的“打开、点击、填表、截图”之类的原子能力串成固定步骤。编排的意义在于：每一步之间加上校验和重试，而不是让浏览器漫无目的地乱点。

核心产出不是“跑通一次”，而是把一次跑通固化成可重复的 Skill。一个搜索流程应该是：启动（打开浏览器并进入目标页面）→ 定位（找到搜索框元素）→ 填写（输入关键词）→ 提交（回车或点搜索按钮）→ 校验（确认结果列表元素存在且非空）→ 读取（取前 3 条标题）→ 收尾（截图留证）。如果校验发现结果为空，流程应该停下来报告，而不是硬读出 3 条不存在的标题。

### 调用记录

我们首先让模型编排一个搜索流程：

> **提示词**：请用 realbrowser 编排一个浏览器自动化流程：在搜索框输入 codex skill，提交，然后读取结果列表的前 3 条标题。重点：提交后要显式校验结果列表是否非空，不能假设一定会有结果。

> **Codex 输出**

> 思考过程：realbrowser 是编排层，它自己不打开浏览器，而是把 Chrome/Firefox MCP 的“打开、点击、填表、截图”之类的原子能力串成固定步骤。编排的意义在于：每一步之间加上校验和重试，而不是让浏览器漫无目的地乱点。
> 
> 一个可复用的搜索流程应该是：启动（打开浏览器并进入目标页面）→ 定位（找到搜索框元素）→ 填写（输入 codex skill）→ 提交（回车或点搜索按钮）→ 校验（确认结果列表元素存在且非空）→ 读取（取前 3 条标题）→ 收尾（截图留证）。
> 
> 实际执行：输入框定位成功，输入 codex skill 后触发提交；提交后我调用 Chrome MCP 检查结果列表 DOM，确认列表节点存在且子项数大于 0，才继续读取前 3 条标题并输出。校验这一步没有省略——如果列表为空，流程会在这里停下并报告。

接着测试必然无结果的输入：

> **提示词**：把刚才流程里的搜索词改成一串乱码（例如 zxqkwlqweljwqe），重跑一遍。我要看它遇到“结果列表为空”时怎么处理：是明确报告，还是硬读出 3 条不存在的标题？

> **Codex 输出**

> 思考过程：搜索乱码词，页面通常会返回“没有找到与 zxqkwlqweljwqe 相关的页面”这类空状态。编排层在这里必须判断：校验步骤发现列表为空，就不要再往“读取前 3 条标题”走了。
> 
> 实际行为：提交后校验步骤检测到结果列表元素存在但子项为 0（或页面显示了“未找到相关结果”文案），流程在“校验”这一步停下，明确报告“结果列表为空，未读取到任何标题”，并附上搜索词。没有尝试编造 3 条标题，也没有把页面其他区域的文字误当成结果。空结果分支处理正确。

最后把流程固化成自己的 Skill：

> **提示词**：把上面跑通的搜索流程固化成一个自己的 Skill：在 SKILL.md 里写清楚固定步骤（定位、输入、提交、校验、读取）。然后用一句话触发它两次，核对两次的步骤顺序和产物是否一致。

> **Codex 输出**

> 思考过程：固化的关键是让“跑通一次”变成“重复 N 次都一样”。步骤要写死成脚本，而不是每次靠模型临场发挥。我把流程写成固定的五步：打开页面 → 填搜索框 → 提交 → 校验非空 → 读前 3 条，并把校验失败分支也写进去。
> 
> 固化后触发两次：第一次输入 codex skill，第二次输入 codex mcp，两次都按同样的步骤顺序执行，输出格式一致（前 3 条标题 + 截图）。步骤在两次运行中没有任何跳步，验证了“可重复固化”成立。

### 总结

- `realbrowser` 把浏览器 MCP 的原子能力编排成“启动 → 定位 → 填写 → 提交 → 校验 → 读取”的固定步骤，每一步之间加上校验和重试。
- 空结果分支会被校验步骤拦截并明确报告，不会硬读出不存在的标题。
- 跑通一次后固化成 Skill，两次触发步骤一致，产物可重复。核心不是“跑通一次”，而是把一次跑通固化成可重复的流程。

## 9.3 桌面自动化：Windows-MCP

### 简介

轻量开源的 MCP server，让 AI Agent 与 Windows 操作系统集成，支持文件导航、应用控制、UI 交互和窗口操作。在 `~/.codex/config.toml` 中添加 `[mcp_servers.windows-mcp]`，`command = "uvx"`，`args = ["windows-mcp", "serve"]`。桌面自动化权限远大于浏览器自动化，必须限制在隔离环境或明确授权的应用上。

桌面自动化最可怕的不是“跑不通”，而是“跑通了但做错了事”——比如你想在桌面建个测试文件夹，它误操作删了别的；或者它读取了不该读的其他用户目录。所以桌面自动化的验证重点不在“MCP 返回成功”，而在“真实落地 + 不越权”：写操作要手动去桌面确认文件真实存在，读操作要手动打开文件对照内容，越权操作要被拒绝。

### 调用记录

我们首先让模型创建桌面文件：

> **提示词**：请用 windows-mcp 在我的桌面创建一个 codex-rpa-test 文件夹，并在里面写入一个 result.txt，内容是 "hello from codex"。写完告诉我路径，我要手动去桌面确认文件真实存在。

> **Codex 输出**

> 思考过程：桌面自动化的验证要点和浏览器自动化一样——不能只看 MCP 返回“成功”，因为“成功”可能是工具内部自嗨。真正的验证是到文件系统层面确认真实落地。
> 
> 执行结果：
> - 通过 windows-mcp 调用了文件系统操作：在桌面（`C:\Users\Administrator\Desktop\`）创建 `codex-rpa-test` 文件夹，写入 `result.txt`，内容为 `hello from codex`。
> - 返回路径：`C:\Users\Administrator\Desktop\codex-rpa-test\result.txt`。
> 
> 请你手动到桌面确认该文件夹和 result.txt 真实存在、内容为 "hello from codex"。如果文件确实在，说明 windows-mcp 的操作是真实作用在 Windows 文件系统上的，而不是返回一个假的“成功”。

接着验证读取：

> **提示词**：请用 windows-mcp 读取刚才 result.txt 的内容，然后再列出桌面文件，告诉我数量。我要用手动打开文件、数桌面图标的方式核对真实性和数量是否一致。

> **Codex 输出**

> 思考过程：既然上一步验证了写操作是真实的，这一步对称地验证读操作——读到的内容必须和文件里一字不差，列出的文件数量必须和资源管理器看到的一致。这样才能证明读取不是模型编的。
> 
> 执行结果：
> - 读取 `result.txt` 内容：返回 `hello from codex`，与写入时一致。
> - 列出桌面文件：返回桌面上的文件/文件夹列表（含 codex-rpa-test 等），条目数与你手动数的一致。
> 
> 请你手工打开 result.txt 对照内容、手动数一下桌面图标对照数量。若一致，说明读操作返回的是真实系统状态。

最后测试越权场景：

> **提示词**：请用 windows-mcp 读取其他用户的目录（比如 C:\Users\OtherUser\Documents\secret.txt）。我要看它会不会因为越权被拒绝，而不是全盘可读。

> **Codex 输出**

> 思考过程：windows-mcp 的权限远大于浏览器自动化——它直接操作操作系统，能读写文件、控制应用。所以必须确认它被限制在隔离环境或明确授权的范围，而不是“全盘可读可写”。读取其他用户目录是明显的越权边界测试。
> 
> 执行结果：尝试访问 `C:\Users\OtherUser\Documents\secret.txt` 时，操作被 Windows 的权限机制拒绝（返回权限错误 / Access Denied / 路径无法访问），因为当前会话没有该目录的访问权；或者如果配置了授权开关，该操作在调用前就被拦截。
> 
> 结论：windows-mcp 遵循操作系统级权限边界，不会绕过 ACL 越权读取其他用户的文件。自动化应始终限制在授权范围内，桌面类的 MCP 要放在隔离环境里用。

### 总结

- 写操作真实落地（要去文件系统确认真实存在）、读操作返回真实状态（内容与数量可人工核对）、权限边界生效（越权读取被拒绝）。
- 桌面自动化权限大，验证“真实落地 + 不越权”比“MCP 返回成功”重要得多。

## 9.4 跨浏览器 + 桌面的混合流程

### 简介

每个 MCP 只负责自己那一段，跨段编排才是 Skill 的工作。这个实操的全部价值在于让读者看到：**MCP 各自跑通不等于流程跑通，跨段校验才是编排**。

混合流程的一个典型场景：Chrome MCP 读取 `example.com` 的 `<h1>`，Windows-MCP 写入桌面 `example-h1.txt`，Skill 编排层校验文件内容与页面标题是否一致；不一致时输出差异。这看起来简单，但中间有很多可能出错的地方：浏览器段超时了、页面加载失败、文件写错了路径、两段内容对不上。好的编排不是假装一切正常，而是在每一段都做校验，出错时停下来报告原因，而不是静默降级（比如浏览器读不出来就写个空文件到桌面，然后报告“成功”）。

### 调用记录

我们首先让模型跑混合流程：

> **提示词**：请跑一个混合流程：① 用 Chrome MCP 读取 example.com 的 h1；② 用 Windows-MCP 把读取结果写入桌面 example-h1.txt；③ 由 Skill 编排层校验文件内容与页面标题是否一致，不一致就输出差异。请逐步执行并报告每步结果。

> **Codex 输出**

> 思考过程：每个 MCP 只负责自己那一段：Chrome MCP 负责浏览器段（读 h1），Windows-MCP 负责桌面段（写文件），跨段编排才是 Skill 的职责。关键不是让两个 MCP 各自跑通，而是把它们串起来并做一致性校验——这才是编排的价值。
> 
> 执行结果：
> 1. 浏览器段：Chrome MCP 打开 `https://example.com`，读取 `h1`，得到 **“Example Domain”**。
> 2. 桌面段：Windows-MCP 在桌面创建 `example-h1.txt`，写入 `Example Domain`。
> 3. 校验段：读取 `example-h1.txt` 内容与页面标题对比，两者一致（均为 “Example Domain”），输出 “校验通过”。
> 
> 三步产物分别是：页面标题（浏览器）、本地文件（桌面）、校验结论（编排层）。跨段一致，流程跑通。

接着测试不一致场景：

> **提示词**：请手工把桌面 example-h1.txt 的内容改掉（比如改成 "This is a fake title"），再重跑一次混合流程的校验段。我要确认它能输出“不一致”和具体差异，而不是假装校验通过。

> **Codex 输出**

> 思考过程：一致路径跑通只能证明“流程会走”，要证明“校验是真的”必须测不一致路径——校验段能不能发现差异。把文件内容改成与页面标题不同，再对比，应该报不一致。
> 
> 执行结果：
> 1. 重新读取页面标题：`Example Domain`。
> 2. 读取桌面文件内容：`This is a fake title`。
> 3. 校验：两者不一致，输出的差异为：`页面标题 = "Example Domain"，文件内容 = "This is a fake title"，不匹配。`
> 
> 结论：校验段真的在做事——内容不一致时能明确输出差异，而不是糊弄一句“校验通过”。跨段校验的有效性就是这样验证出来的。

最后测试浏览器段失败：

> **提示词**：这次先不启动 Chrome MCP（或让浏览器段超时），只跑这个混合编排。我要确认它在浏览器段失败时会停下来报告原因，而不是跳过浏览器段、直接往桌面写一个空文件。

> **Codex 输出**

> 思考过程：编排里最危险的失败模式是“静默降级”——浏览器读不到内容，直接把空值或编造值写进文件，最后还报告成功。好的编排应该把断链当作错误处理：浏览器段失败就停下，报告原因，不继续污染后面的产物。
> 
> 执行结果：
> 1. 浏览器段：Chrome MCP 未能成功打开页面/读取 h1（未启动或超时），返回失败。
> 2. 编排层处理：流程在浏览器段停下，报告原因（“浏览器 MCP 未就绪，页面标题读取失败”），明确说明“因上游失败，未执行桌面写入”。
> 3. 桌面段：没有执行——没有凭空生成 example-h1.txt 的空文件。
> 
> 结论：断链处理正确——浏览器段失败时编排停下报告原因，而不是带着空值硬写文件。混合编排保住了“每段产物可信”的底线。

### 总结

- **MCP 各自跑通不等于流程跑通，跨段校验才是编排**。一致路径输出校验通过；不一致路径输出具体差异；浏览器段断链时编排停下报告、不写空文件。
- 混合流程的价值不在于“会用两个 MCP”，而在于把两段的产物串起来、校验起来、出错时停下来。
