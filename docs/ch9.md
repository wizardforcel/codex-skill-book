# 第9章 运营自媒体

自媒体不是“写一篇就发”，而是一条链：选题、来源约束、写作、独立审稿、配图、平台适配、进草稿箱，最后才是人工发布。这一章介绍三个 Skill：一个管公众号从选题到草稿箱，一个把已有作品适配到小红书/抖音/视频号草稿箱，一个负责封面与图文卡片的视觉物料。自媒体本质上是一条明确的流水线，把选题、来源、写作、配图、平台适配分开处理，质量才有可能稳定，而不是每次看运气。

## 9.1 公众号从选题到草稿箱

### 简介

`publish-gzh` 覆盖公众号的完整生产链：选题、来源约束、中文写作、独立审稿、可选语义配图、确定性校验，最终进入草稿箱。它的设计重点是把“审稿”作为独立环节，而不是写作的附属；并且把“发布”与“公开推送”分开：自动化的终点是草稿箱，最后按下群发按钮的仍然是人。公众号生产链的每一步都有产物和检查点，审稿独立于写作，这是它跟随手写完就发最大的区别。

它有硬边界：只用有来源的事实，绝不编造人物、日期、媒体背书、交易结果；不把量化分析定位成投资建议；不保存 API Key、微信凭据、Cookie；文章内容没有通过运营商确认前不发给外部向量 API。

### 调用记录

**我**：我想写一个公众号选题：“Codex Skill 和 MCP 的区别”。

**Codex**：按 `publish-gzh` 的流程，第一步不是写正文，而是判断模式并输出 Checkpoint 1 的任务清单：

```yaml
mode: original
audience: ...
reader_problem: ...
core_conclusion: ...
article_path: ...
source_pack:
  - path_or_url: ...
    intended_claims: [...]
assets:
  image_dir: ...
  image_index: ...
publish_requested: false
risks: [...]
```

`source_pack` 里的 `intended_claims` 就是“每一条要写的观点，对应哪份来源”。缺少事实来源时，不能用猜测补齐——这一步会直接标 `NEEDS_INPUT`。

**我**：那两个概念的区别，我凭印象写行不行？

**Codex**：不行。它的写作规则写得很直接：`每个关键数字、战绩、媒体背书、人物经历都绑定来源；没有来源就删掉`。像“MCP 是连接外部工具的标准、Skill 是工作说明书”这类定义，要从官方文档或仓库 README 里取；取不到就标成未解决，而不是编一个看起来合理的解释。

**我**：写完谁来审？

**Codex**：Checkpoint 3 是独立审核，最好用独立上下文或子 Agent。审核只输出 `PASS` 或 `FAIL`，先报阻断项再报文风问题，并给出精确位置。写作和审核分开，避免“自己写自己夸”。

**我**：审过就能发吗？

**Codex**：还不能。Checkpoint 5 要跑确定性校验，校验非零退出会阻断发布。Checkpoint 6 才调用发布工具进草稿箱，主题是 `orangeheart`，并记录返回的 Media ID；最终公开群发仍然要你在微信后台手动完成。文章 frontmatter 作者要写 `桥博士`，不接受 `宽论`。

**我**：搜索 MCP 能找到 publish-gzh 的公开教程吗？

**Codex**：没有检索到这个项目的专门教程，只有公众号排版和自动发布的泛化文章。它们能说明“写作 → 校验 → 草稿箱 → 人工群发”的大致链路，但具体检查点和命令不同。本节仍以仓库 `SKILL.md` 的 Checkpoint 1–6 为依据，不把别家工具的命令写进来。

把这一节放回整条链路里看，它只是其中一段；真正动手时不必追求一次全对，先把命令跑通、把输出对上，遇到报错再回来查对应位置，往往比从头读一遍更快。

### 总结

这一节的内容说起来不少，真正值得带走的是下面几条；把它们串起来看一遍，比单独记某一条更有用。

- 流程是检查点式的：任务清单 → 写作 → 独立审核 → 配图 → 校验 → 草稿箱。
- 写作前先列 `source_pack`，每条观点绑定来源；没有来源就删，不猜。
- 审核是独立环节，只给 PASS/FAIL，阻断项优先、给精确位置。
- 自动化止于草稿箱；公开群发永远由人按下。
- 凭据、Cookie、私密素材不能进 Skill 或 git。

## 9.2 跨平台草稿生成与上传

### 简介

`filler` 把已经完成的作品转成平台发布草稿：AI 写标题文案，CLI 校验素材，Playwright 自动上传到小红书、抖音、视频号、公众号的草稿箱。它和 `publish-gzh` 互补：一个负责“从无到有写公众号”，一个负责“把已有内容适配到多平台草稿箱”。把成品转成平台草稿时，真正的底线是公开按钮绝不自动点；能不能安全停在草稿箱，是衡量一个发布工具是否值得信任的标准。

它的硬边界比“能自动点按钮”更重要：不点立即公开的发布/提交按钮；即时发布只做到保存草稿、验证保存、关闭专用浏览器 profile；不绕过验证码、登录检查、私有 API 或平台风控；抖音桌面创作中心可能不保存草稿，要如实提醒。

### 调用记录

**我**：把 9.1 的文章交给 filler，生成小红书版本，只到草稿箱，不实际发布。

**Codex**：先做引导式提问，最多 1 到 3 个未决选择，给出推荐项：

```text
1. 是否定时：不定时 (Recommended) / 单条定时 / 批量定时
2. 平台：小红书+抖音 (Recommended) / 三平台 / 自定义
3. 合集策略：自动选择宽泛合集 (Recommended) / 跳过合集 / 我指定合集
```

确认后先跑 `preflight`，检查草稿填充包、Playwright、profile 有效性；没有 profile 会创建，但登录必须由人完成一次。

**我**：它会原样搬运公众号文章吗？

**Codex**：不会。它有 `copy-generate` / `copy-select` 两个环节：AI 先写候选标题与文案，CLI 校验，再由你选择；然后生成 `draft-plan` 指定素材顺序、标题来源、标签与合集。平台适配是独立步骤，不是把公众号长文直接塞进小红书。

**我**：实际能跑到哪一步？

**Codex**：本机没有完成小红书/抖音的登录 profile，`preflight` 和打开编辑器会停在 `needs_human`，要求人工登录。这属于技能的硬边界：它不绕过登录、不假装“打开了一个 URL”就等于“进入了可编辑的发布编辑器”。所以本次的真实结论是：文案适配与草稿计划可以生成，真正的草稿箱上传需要你先登录专用 profile。

**我**：那它怎么验证“上传成功”？

**Codex**：即时任务必须在保存草稿后回读验证，确认保存成功再关闭专用 profile；如果平台无法验证草稿保存，就停 `needs_human`，不宣布成功。`publish-result.json` 和 `draft-fill-result.json` 只是本地证据，不提交到 git。

**我**：搜索 MCP 能找到 filler 的公开教程吗？

**Codex**：同样没有项目级教程，检索结果是小红书/抖音发布工具的泛化介绍。能确认的共性只有一条：自动化到草稿箱为止，公开按钮由人点。本节关于 `preflight`、登录不绕过、保存后回读验证的细节，仍以仓库 `SKILL.md` 为准。

这些步骤看起来零散，其实前后是有因果的：前一步的产物就是后一步的输入，中间哪一环没对上，后面就会以各种奇怪的方式报错。

### 总结

这一节的内容说起来不少，真正值得带走的是下面几条；把它们串起来看一遍，比单独记某一条更有用。

- `filler` 把成品适配到多平台草稿箱：写标题、校验素材、Playwright 上传。
- 自动化只到草稿箱；立即公开发布永远由人点。
- 不绕过验证码、登录、私有 API 和平台风控；无法验证保存就报 `needs_human`。
- 引导式提问最多 1–3 个未决选择，能推断的就先推断并让用户确认。
- 小红书可保存草稿；抖音桌面创作中心可能不保存草稿，技能会提前警告。

## 9.3 图文视觉物料的生成

### 简介

`guizang-social-card-skill` 把“找图”变成“按内容生成匹配的视觉物料”：小红书 3:4 图文组图、公众号 21:9 + 1:1 封面对、Live Photo 实况卡片、截图型产品贴等。它的核心原则是“表达优先”——不是把文字挤进海报，而是把内容变成清晰的视觉论证：一页里读者一眼该看懂什么、哪条证据支撑它、哪些字必须大、哪些可以删。视觉物料不是把文字硬塞进模板，而是让内容本身决定版面；这条原则比任何一套现成模板都重要。

它明确划了能力边界：强项是旅行、职场、推荐；图文/截图型可以接；而纯菜品摆盘、日常 OOTD 全身照、梦核氛围装饰、纯摄影展示，会直接说“不在能力范围内”，不硬套模板。

### 调用记录

**我**：用 9.1 的标题和核心结论生成 3 张小红书图文卡片。

**Codex**：先按规格确定画布：小红书静态卡片 3:4，画布 `1080 × 1440`；公众号封面是 `21:9` 主图 + `1:1` 方图，两套要放在同一个 HTML 里做视觉检查。任务产物放任务文件夹，不能散落在 Skill 根目录。

**我**：先生成第一张看看。

**Codex**：生成到 `local-tests/xhs-demo/card.html`，结构是：

```text
kicker     CODEX 入门 · 01
h1         Skill 和 MCP 到底差在哪？
rule       强调线
points     01 MCP 负责把外部工具“连上”
           02 Skill 负责决定“怎么用”
           03 缺一个，流程都跑不稳
foot       1080 × 1440 · 小红书 3:4 图文卡片
```

画布严格 1080×1440，标题用大字号，三条要点短句化，页脚标注规格。真实文件已生成在任务目录中，不是一张通用模板图。

**我**：怎么保证不是套模板？

**Codex**：技能的“表达优先”要求每页先回答四个问题：一眼要懂什么、证据在哪、哪些字必须大、哪些该删。然后再做版面。分类路由也会约束：比如“美食”只接食谱方向，不接菜品摆盘大片；“穿搭”只接精选/胶囊方向，不接日常 OOTD 全身照。超出范围时，入口就明说做不了，而不是生成一张看起来还行但跑题的图。

**我**：公众号封面怎么做？

**Codex**：一组两张：`21:9` 主封面和 `1:1` 方封面，必须放在同一个 HTML 文件里，附一个并排预览区方便肉眼检查；两张的标题不能互相硬塞，`21:9` 的长标题不能压缩进方图。

如果只记住一句，那就是：先让最小链路真实跑通，再谈优化和自动化；跳过验证直接堆功能，最后往往要花更多时间回头补。

### 总结

这一节的内容说起来不少，真正值得带走的是下面几条；把它们串起来看一遍，比单独记某一条更有用。

- 视觉物料的核心是“表达优先”：先决定一页要传达什么，再排版。
- 小红书静态卡片是 3:4 / 1080×1440；公众号是 21:9 + 1:1 一对。
- 产物放任务文件夹（如 `local-tests/<slug>/`），不污染 Skill 根目录。
- 分类路由会明确接或不接：超出能力范围就直说，不硬套通用模板。
- 真实生成的第一张卡片是 HTML 文件，版式由内容结构决定，不靠套模板。
