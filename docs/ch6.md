# 第6章 搭建知识库

知识库的价值不在于“存了很多笔记”，而在于“需要的时候能搜到，并且敢用”。这两件事差得很远：全文搜索能给你十条结果，但其中可能互相矛盾、来源不明、甚至来自还没入库的草稿。这一章介绍两套 Obsidian 知识库 Skill，一套是规则优先的离线 RAG，一套是把 vault 当持久记忆的轻量方案，最后用一个结构报告把“能搜到”和“敢用”区分开。知识库的搭建不是收藏游戏，而是建立一套“敢用”的系统；这一章会一步步演示，怎么让每一条回答都有据可查、有源可追。

## 6.1 规则优先的离线 RAG

### 简介

`md-vault-rag-manager` 核心是一条引导式工作流：初始化 vault 时把规则区和导入区分开，正式知识必须有来源回证，检索是关键词 + 标签 + 路径 + 索引的混合方式，回答必须能追溯到原文。它解决的是“能搜到”和“敢用”之间的差距。

RAG 是什么？Retrieval-Augmented Generation 的缩写，中文叫“检索增强生成”。简单说，就是让 AI 在回答问题之前，先去你的笔记库里搜相关内容，再基于搜到的内容回答，而不是凭空胡说。离线 RAG 就是所有数据都存在你自己的电脑里，不需要上传到云端。

## 6.2 插件市场安装与持久记忆

### 简介

`obsidian-knowledge` 把 Obsidian vault 作为 Agent 的记忆层，支持搜索笔记、保存可复用知识、维护索引和链接，适合跨会话记住上下文。与 `md-vault-rag-manager` 的严格 RAG 工作流形成轻/重对照。

持久记忆是什么意思？就是 AI 不会在每次对话结束后就把一切都忘掉，而是把重要信息保存下来，下次对话的时候还能想起来。这就好比你有一个笔记本，每次学完新东西都写下来，下次复习的时候翻开笔记本就能看见。

### 调用记录

我们先让模型演示跨会话记忆：

```
我：会话中让 Codex 记住“我的项目代号是 bluebird”，结束会话后新开一个会话询问，验证跨会话记忆是否生效。
```

模型给出如下回复：

```
> obsidian-knowledge 把 Obsidian vault 作为 Agent 的记忆层，支持搜索笔记、保存可复用知识、维护索引和链接，适合跨会话记住上下文。

> 已将“我的项目代号是 bluebird”保存到知识库笔记中。

# 知识保存确认

笔记标题：项目代号记录
笔记内容：我的项目代号是 bluebird
保存位置：vault/notes/project-code.md

知识已持久化到本地 vault，可在后续会话中检索。
```

接着测试跨会话记忆：

```

### 总结

- `obsidian-knowledge` 把 Obsidian vault 作为 Agent 的记忆层，支持搜索笔记、保存可复用知识、维护索引和链接。
- 适合跨会话记住上下文，新开会话后仍能检索到之前保存的知识。
- 与 `md-vault-rag-manager` 的严格 RAG 工作流形成轻/重对照。

## 6.3 带证据的检索与结构报告

### 简介

回答必须能追溯到原文，这是知识库“可用”和“能搜到”之间的分界线。结构报告应逐条列出正式知识的来源路径和检索命中证据。

什么叫“有据可查”？就是说 AI 回答你的问题时，不只是给你一个结论，还要告诉你这个结论是从哪里来的，是哪篇笔记的哪一行。这样你就可以自己去查看原文，确认 AI 是不是没胡说八道。

### 调用记录

我们先让模型输出结构报告：

```
我：让 Skill 输出结构报告，要求列出每条正式知识的来源路径和最近一次被检索命中的次数；如果只有“知识库包含 N 篇笔记”的总量统计，说明它还在做“搜索”而不是“RAG 管理”。
```

模型给出如下回复：

```
# 结构报告：知识库检索证据追溯

报告时间：2026-11-23
vault 路径：vault/

## 正式知识列表

| 知识内容 | 来源路径 | 最近检索命中次数 | 最后命中时间 |
|---------|---------|-----------------|-------------|
| Alpha 项目预计 2026 年 6 月完成第一阶段 | vault/notes/project-timeline.md | 3 | 2026-11-23 10:15 |
| Alpha 项目第一阶段 6 月底前交付原型 | vault/notes/milestone-confirm.md | 2 | 2026-11-23 09:30 |
| Alpha 项目第一阶段延期至 8 月 | vault/notes/delay-notice.md | 5 | 2026-11-23 11:00 |

## 检索统计

- 总检索次数：10
- 命中笔记总数：3
- 存在矛盾的笔记：1 篇（delay-notice.md 与 project-timeline.md 冲突）

## 结论

这不是简单的“搜索”，而是 RAG 管理：每条正式知识都有来源路径可追溯，检索命中次数有记录，矛盾信息被标记而非平滑处理。如果只输出“知识库包含 3 篇笔记”的总量统计，则说明还在做“搜索”而不是“RAG 管理”。
```

### 总结

- 回答必须能追溯到原文，这是知识库“可用”和“能搜到”之间的分界线。
- 结构报告应逐条列出正式知识的来源路径和检索命中证据。
- 如果只输出“知识库包含 N 篇笔记”的总量统计，说明它还在做“搜索”而不是“RAG 管理”。

## 6.4 接入实时文档知识库：Context7 MCP

### 简介

Context7 是当前文档/知识类 MCP 中热度最高的项目之一，定位是“为 AI Agent 提供实时、版本精确的文档与代码示例”。它解决模型训练数据滞后的问题：回答库或框架用法时，按需拉取当前版本文档并给出可追溯来源。与 6.1—6.3 的分工是：Vault 管理个人知识，Context7 管理外部技术文档知识；两者都由 Skill/工作流决定“什么时候查、查哪个版本、如何引用证据”。

模型训练数据滞后是什么意思？就是说 AI 学习的数据有一个截止日期，在这个日期之后发生的新技术、新版本，AI 可能不知道。Context7 就是让 AI 在需要的时候，去查最新的官方文档，这样回答就不会过时了。

### 调用记录

由于 `context7` 未在本地安装，且网络检索无结果，按要求合理推测其调用记录：

```
我：让 Codex 通过 Context7 查询一个你本地项目正在使用的库（例如 react 或 fastapi）的当前版本文档，要求回答中同时给出库版本、文档来源/链接、关键 API 用法；再与不查文档时的回答对比，检查是否出现“旧版写法”被纠正。最后把来源链接写入 6.1 的 vault 笔记，验证“外部文档知识库 → 个人知识库”的回证链路。
```

模型给出如下回复：

```

## 对比不查文档时的回答

不查文档时，模型可能会给出基于旧版训练数据的回答，比如使用 `@app.on_event("startup")`（已在较新版本中弃用，应改为 lifespan 事件）。查询 Context7 后，模型会纠正为：

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 启动逻辑
    yield
    # 清理逻辑

app = FastAPI(lifespan=lifespan)
```
