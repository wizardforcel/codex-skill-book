# 第12章 结语：边界与判断力

走到这里，你已经见过写作、视频、开发、逆向、知识库、RPA、论文、自媒体、选股、命理十类场景。它们看起来毫不相干，但底层是同一条分界线：Skill 可以把流程、工具和固定动作交给你，**判断仍然在你手里**。这一章用两个 Skill 收束：一个逼你想清楚需求，一个帮你把自己的 SOP 固化成技能。把前面十一个场景串起来再看，你会发现真正值钱的不是某一套技能，而是你判断该在哪一步停下来、哪些结论该由自己负责的那种能力。

## 12.1 Skill 不能替你做的事

### 简介

`grill-me` 是一个“无情追问”的 Skill：它把你的计划、决策或想法画成一棵设计树，每一轮把“前置条件已经确定、现在就能问”的问题一次性摆到你面前，每个问题都给出推荐答案，然后等你回答，再推进下一轮。它的价值是**暴露盲区**，不是**给出答案**。看到这里你会发现，全书反复出现的其实是一条线：工具负责流程，判断负责方向，谁都替不了谁。

这和前面章节的判断是同构的：因子有没有经济逻辑、命理解读有没有越界、选股数据够不够，这些问题 Skill 无法替你回答。它能做的是把“你还没想清楚的地方”逐条摆出来。

### 调用记录

**我**：我在想要不要辞职做独立开发。

**Codex**：`grill-me` 实际只是入口，它转去 `grilling` 技能。规则是：先把决策画成设计树，按轮次问“当前 frontier”上的问题，每个问题给推荐答案，然后等回答。第一轮我会问这些：

```text
❓ Q1 - 现金流缓冲：你现在的存款能覆盖多少个月的生活成本？
➡️ 建议先算到 12 个月；少于 6 个月时，独立开发的风险下限过高。

❓ Q2 - 需求验证：你打算做的产品，是否已经有真实用户愿意付费或明确预订？
➡️ 建议先拿到 3 个真实付费意向，再辞职；只有“朋友说不错”不算验证。

❓ Q3 - 家庭责任：未来 12 个月是否有必须由你承担的固定支出或照护责任？
➡️ 建议把不可压缩支出单列，不并入“生活成本”估算。

❓ Q4 - 退出条件：如果 9 个月后收入仍为 0，你的止损动作是什么？
➡️ 建议提前写成一个可执行动作，例如“回到兼职/接外包/停止项目”，不要只写“再想想”。
```

**我**：那你直接告诉我该不该辞职吧。

**Codex**：不能。`grilling` 的规则写得很清楚：事实由它去找，决策是你的；每一轮都要等你回答才能重算 frontier，最后还要你确认“已经达成共同理解”。它不会替你拍板。

**我**：那它和前面那些领域 Skill 有什么共同点？

**Codex**：共同点是“判断不可外包”。第 10 章的因子有没有经济逻辑、第 11 章的解读有没有越界，都不是 Skill 能替你回答的；它们能做的是把证据、字段、边界和追问摆出来，让你做决定时不再靠感觉。

**我**：如果第一次没跑通，通常先查哪里？

**Codex**：最常见的是把'会用技能'当成'会判断'：工具能给你流程和证据，但该不该做、做到哪一步，仍然要你自己定。把这一步记下来，下次再遇到同类问题时能少走不少弯路。

把这一节放回整条链路里看，它只是其中一段；真正动手时不必追求一次全对，先把命令跑通、把输出对上，遇到报错再回来查对应位置，往往比从头读一遍更快。

### 总结

这一节的内容说起来不少，真正值得带走的是下面几条；把它们串起来看一遍，比单独记某一条更有用。

- `grill-me` / `grilling` 用设计树和轮次追问，把隐藏假设逐条暴露。
- 每个问题给推荐答案是“帮你思考”，不是“替你做决定”。
- 事实由 Agent 去查，决策由用户来做；frontier 清空且用户确认才算结束。
- 领域 Skill 的判断边界同理：因子逻辑、命理解读、投资风险，最终仍由你负责。
- Skill 的价值是暴露盲区，不是给出答案。

## 12.2 从使用 Skill 到设计自己的 SOP

### 简介

第 1 章用 `skill-creator` 是为了理解机制；到这里，你已经走过十一个场景，有了“什么工作流值得固化”的直觉。收束原则有三条：**一个 Skill 只做一件事**；**description 前载触发词**；**装上大量技能之前，先确认每一个都有明确的触发边界**。学会把一个自己的 SOP 固化成技能，等于把'会用别人的技能'升级成'会造自己的技能'，这大概是这本书最好的收尾方式。

用一个日常反复出现的 SOP 来收尾：CSV 列名 / 空值率 / 异常值分布检查。

### 调用记录

**我**：我每周都要检查 CSV 的列名、空值率和异常值分布，想把它固化成 Skill。

**Codex**：用内置 `skill-creator` 的初始化脚本生成骨架：

```powershell
py C:\Users\Administrator\.codex\skills\.system\skill-creator\scripts\init_skill.py csv-audit --path D:\sop
# Initializing skill: csv-audit
#    Resources: none (create as needed)
# [OK] Created skill directory: ...\sop\csv-audit
# [OK] Created SKILL.md
# [OK] Created agents/openai.yaml
```

生成的文件只有两个：`SKILL.md` 和 `agents/openai.yaml`。模板里的 description 是占位的：

```yaml
description: "[TODO: Briefly describe what this skill does and when it applies.]"
```

**我**：description 应该怎么写？

**Codex**：收紧到一句话，并且把用户会说的原话放进去，这是触发词：

```yaml
name: csv-audit
description: 审计 CSV 文件的列名、空值率和异常值分布；当用户说“检查这个 CSV”“看看数据质量”“列名/空值/异常值”时使用。
```

**我**：要不要加 `scripts/`？

**Codex**：先不要。这个 SOP 的步骤只有三步：读表 → 统计每列空值率 → 对数值列算分位数并标异常。全部能写进 `SKILL.md`，不需要脚本。只有当同一段统计代码被反复重写、或需要确定性执行时，才加 `scripts/`。技能能简单就简单。

**我**：怎么验证？

**Codex**：用 `skill-creator` 的 `quick_validate.py`，中文技能在 Windows 上要加 UTF-8 模式：

```powershell
uvx --with pyyaml python -X utf8 C:\Users\Administrator\.codex\skills\.system\skill-creator\scripts\quick_validate.py D:\sop\csv-audit
# Skill is valid!
```

**我**：那我是不是可以把所有能想到的 SOP 都装上？

**Codex**：不建议。`skill-creator` 的原则是“一个技能只做一件事”，`description` 负责精准路由。技能太多而触发词互相重叠时，Codex 会在不该用的时候用错技能；先确认每一个都有明确边界，再装下一个。装完后用一句自然的隐式提示测一次触发，比如“帮我看看这个 CSV 的质量”，确认它命中 `csv-audit` 而不是别的技能。

**我**：按这个流程做，最容易卡在哪一步？

**Codex**：最常见的是把'会用技能'当成'会判断'：工具能给你流程和证据，但该不该做、做到哪一步，仍然要你自己定。遇到时先按本节记录的顺序排查，通常都能定位到具体原因。

这些步骤看起来零散，其实前后是有因果的：前一步的产物就是后一步的输入，中间哪一环没对上，后面就会以各种奇怪的方式报错。

### 总结

这一节的内容说起来不少，真正值得带走的是下面几条；把它们串起来看一遍，比单独记某一条更有用。

- 从“使用 Skill”到“设计 SOP”：先找出反复出现、步骤稳定的工作流。
- 一个 Skill 只做一件事；description 前载触发词，用用户的原话来写。
- 能写在 `SKILL.md` 里的流程就不要加脚本；只在需要确定性执行时加 `scripts/`。
- 用 `quick_validate.py` 校验，中文/Windows 环境注意 UTF-8。
- 装技能之前先确认触发边界；技能越多，路由越需要克制。

全书到这里收束：Skill 和 MCP 把工具、流程、检查点交到了你手里，但它们不替你判断。选哪个模型、因子是否有经济逻辑、解读是否越界、这笔钱该不该投、这份工作该不该辞——这些问题的答案，仍然在你自己手里。
