# 第11章 AI 命理：从排盘引擎到多术数解读

命理类 Skill 最容易出问题的地方，是让模型“自己排盘”。纯 LLM 排八字经常把日柱、日主、格局算错，一步错、后面全错。这一章的核心不是教你看命，而是看一套 AI 命理工具如何把“计算”和“解读”分开：排盘、起卦、星盘由本地确定性脚本算出来，模型只负责在事实层之上做解读，并且必须守住边界。命理类内容特别容易让人放松对'准确性'和'边界'的要求，所以这一章把'谁在算、算没算对、是否越界'当成贯穿始终的主线。

## 11.1 计算引擎层：八字 + 紫微，算法排盘不靠 LLM 猜

### 简介

`bazi-ziwei-skill`（技能名 `bazi-ziwei`）做八字四柱、紫微十二宫、大运流年的排盘，并提供三种模式：八字独立、紫微独立、综合印证。它最硬的一条规则写在 SKILL.md 里：**绝对不要让 AI 自己排八字或紫微**，必须调用算法层脚本 `calculator/dist/run-chart.js`，因为纯 LLM 排盘会把日柱 → 日主 → 格局 → 用神整条链算歪。命理类 AI 工具最重要的一条纪律，是排盘必须由算法现算，模型只能负责解读；这一节就是这条纪律的完整落地示范。

综合印证的增量不是“两种说法都讲一遍”，而是两套独立体系的结论交叉对账。

### 调用记录

**我**：输入 2000-01-01 12:00、男，选综合印证，只要事实层，不要解读。

**Codex**：按 Step 0 先确认模式，然后进入 Step 1 排盘。脚本是预编译好的 Node 程序，先把依赖装齐：

```powershell
cd calculator
npm install --no-audit --no-fund
# added 4 packages in 4s

node dist/run-chart.js --year=2000 --month=01 --day=01 --hour=12 --minute=00 --gender=male > chart.json
# rc=0，chart.json 30695 字节
```

**我**：直接跑就出结果了吗？

**Codex**：第一次并不顺。`run-chart.js` 报：

```text
Error: Cannot find module 'lunar-typescript'
```

说明仓库只带了编译产物、没带 `node_modules`。补一句 `npm install` 之后才成功。这也是很真实的部署坑：拿到预编译脚本，不等于拿到依赖。

**我**：事实层里有什么？

**Codex**：`chart.json` 的顶层是 `bazi` 和 `ziwei`。真实字段：

```text
bazi keys: birthInfo, siZhu, dayMaster, shiShen, zhangSheng, naYin, dayunStart, dayun, cangGan, enrichment
ziwei keys: birthInfo, lunarDate, siZhu, yinYang, mingGongIndex, shenGongIndex, wuXingJu, gongs

四柱: 己卯 丙子 戊午 戊午
日主: 戊
大运条数: 9
```

再转成文墨天机风格的文本盘：

```text
node dist/dump-text.js --input=chart.json --output=chart.txt
# Text dump written to chart.txt

紫微斗数命盘
├基本信息
│ ├性别 : 男
│ ├阳历 : 2000-01-01 12:00
│ ├农历 : 1999年冬月廿五
│ ├节气四柱 : 己卯 丙子 戊午 戊午
│ ├阴阳 : 阳男
│ ├五行局 : 土五局
│ └命宫=午  身宫=午
├生年四化
│ └天梁化科 · 武曲化禄 · 贪狼化权 · 文曲化忌
├命盘十二宫
│ ├命宫[庚午][命]
│ │ ├主星 : 紫微
│ │ ├辅星 : 禄存·天喜
│ │ ├大限 : 5-14虚岁
```

**我**：这些事实能直接拿来交叉对账吗？

**Codex**：可以，但只对“事实层”做对账：四柱、日主、命宫、主星、五行局、大运起止。综合印证要求先跑八字和紫微的独立分析拿到中间报告，再喂给综合提示词；如果说“两套体系在事业方向上是否一致”，那一步仍然属于解读，需要单独做，且要标明是推断不是排盘事实。

**我**：为什么不让模型自己算？

**Codex**：SKILL.md 的原文是：`纯 LLM 排盘会错排日柱 → 日主 → 格局 → 用神，全链失真`。算法层不可绕过，模型只能读 `chart.json` / `chart.txt`。这就是“可复现”的第一层：同一组出生信息、同一份脚本，永远得到同一组四柱和宫位。

**我**：这一步有没有什么容易被忽略的细节？

**Codex**：最常见的是让模型自己排盘：日柱、卦象一旦算错，后面的解读再顺也没有意义。先别怀疑工具本身，多数情况是环境、路径或前置条件没对上。

把这一节放回整条链路里看，它只是其中一段；真正动手时不必追求一次全对，先把命令跑通、把输出对上，遇到报错再回来查对应位置，往往比从头读一遍更快。

### 总结

这一节的内容说起来不少，真正值得带走的是下面几条；把它们串起来看一遍，比单独记某一条更有用。

- 八字/紫微必须先由 `run-chart.js` 排盘，模型不自己算。
- 排盘产物是结构化 `chart.json`（四柱、十神、藏干、大运、十二宫、四化）和可读 `chart.txt`。
- 真实样例：四柱“己卯 丙子 戊午 戊午”，日主戊，命宫午、主星紫微、土五局、大运 9 条。
- 综合印证 = 两套独立体系的事实与结论对账，不是把两种说法混在一起。
- 预编译脚本仍需 `npm install` 补依赖，否则会报 `Cannot find module`。

## 11.2 占卜类（一）：六爻 / 梅花，一事一断的确定性起卦

### 简介

`taibu-divination` 是太卜的占术工具集，包含 15 种本地计算引擎：八字、紫微、六爻、梅花易数、奇门遁甲、大六壬、小六壬、太乙、塔罗、西方占星、黄历等。计算引擎随 Skill 打包在 `scripts/vendor/taibu-core.bundle.mjs`，本地运行，无需安装依赖，只要求 Node.js 18+。一事一断的占卜强调的是确定性：同一组输入永远得到同一副卦，可复现正是它和编故事之间的分界线。

它把“起卦”和“解读”分开：起卦是确定性计算，同一组输入永远得到同一组卦象；解读是模型在卦象基础上的生成。六爻的 `method: "number"` 用数字起卦，`auto` 模式才是随机三钱；要复现就必须用 `number`、`select` 或固定输入。

### 调用记录

**我**：用数字起卦问“这次合作的结果”，要求输出本卦、互卦、变卦、动爻、体用关系；再用同一组数字跑一次，确认两次卦象完全一致。

**Codex**：先看工具和参数：

```powershell
node scripts/taibu.mjs list
# liuyao 六爻排卦 / meihua 梅花易数起卦 / qimen 奇门 / daliuren 大六壬 ...

node scripts/taibu.mjs schema liuyao
# numbers: 2-3 个正整数：第一数取上卦，第二数取下卦，第三数取动爻
```

按 schema，数字起卦的调用是：

```powershell
echo '{"question":"这次合作的结果","yongShenTargets":["兄弟"],"method":"number","numbers":[7,8,5],"date":"2026-11-03T12:00:00"}' | node scripts/taibu.mjs call liuyao -
```

真实输出：

```text
本卦: 山地剥（乾宫·金）
变卦: 风地观（乾宫·金）
动爻: 六五
六五爻辞: 六五：贯鱼，以宫人宠，无不利。
时间: 丙午 戊戌 辛巳 甲午
```

**我**：再跑一次，哈希对比。

**Codex**：同一组数字、同一日期，两次输出 SHA-256 完全一致：

```text
6eec90192690f5a4cc702054d58e3b2a2d030876b31f578c812c419babe90947  (两次相同)
```

这证明卦象来自脚本计算，而不是模型临场“编卦”。如果换成 `method: "auto"`，每次结果随机；要复现就必须像这样指定 `number` 或 `select`。

**我**：那梅花呢？

**Codex**：同一个工具集里 `meihua` 支持年月日时、物数声数、字占、丈尺、方位、报数起卦，输出本卦/互卦/变卦与体用生克。它的起卦同样是脚本算的，模型只负责按方法文档解读。

**我**：如果第一次没跑通，通常先查哪里？

**Codex**：最常见的是让模型自己排盘：日柱、卦象一旦算错，后面的解读再顺也没有意义。把这一步记下来，下次再遇到同类问题时能少走不少弯路。

这些步骤看起来零散，其实前后是有因果的：前一步的产物就是后一步的输入，中间哪一环没对上，后面就会以各种奇怪的方式报错。

### 总结

这一节的内容说起来不少，真正值得带走的是下面几条；把它们串起来看一遍，比单独记某一条更有用。

- 太卜的 15 个引擎随 Skill 打包，本地 Node 18+ 直接运行，无需联网。
- 起卦是确定性计算；六爻数字起卦用 `method:"number"` + `numbers`，不要用随机的 `auto` 去谈复现。
- 真实样例：山地剥 → 风地观，动爻六五；两次输出哈希完全一致。
- 解读必须引用盘面证据（卦名、爻位、干支），不能生造盘面没有的格局名或神煞。
- 有“一次一断”的边界：六爻/梅花占的是具体一件事，不用来推出生时辰或长期命盘。

## 11.3 占卜类（二）：奇门遁甲 / 大六壬，时空决策的排盘 JSON

### 简介

奇门和大六壬是“时空决策”类术数，输入需要时间 + 地点 + 具体问题。太卜用确定性脚本排盘，以结构化输出让 Agent 在解读前核对时间、历法、规则集和盘面字段；`horosa-agent` 覆盖紫微、大六壬、奇门、太乙、金口诀、三式合一等更广范围。奇门与六壬这类时空决策术数，输入的是时间和一个具体问题，排盘结果也必须能逐项核对，而不是一个笼统的结论。

关键不是“算得多玄”，而是盘面可核对：时间是否与输入一致、局数与值符值使是否显式给出、四课三传是否完整。

### 调用记录

**我**：对一次谈判择时，先给奇门排盘 JSON（时间、局数、值符值使、九宫字段），确认与输入一致后再解读。

**Codex**：奇门参数需要年、月、日、时：

```powershell
echo '{"year":2026,"month":11,"day":3,"hour":12,"minute":0,"timezone":"Asia/Shanghai","question":"这次谈判择时"}' | node scripts/taibu.mjs call qimen -
```

真实输出：

```text
四柱: 丙午 戊戌 辛巳 甲午
节气: 霜降 (阴遁5局 · 上元)
值符 (大局趋势): 天芮星
值使 (执行枢纽): 死门
九宫: 坎1 玄武/天蓬/休门/壬；坤2 值符/天芮/死门/辛戊；震3 六合/天冲/伤门/庚 ...
全盘: 星伏吟、门伏吟
```

时间与你输入的 2026-11-03 12:00 一致，局数“阴遁5局·上元”、值符天芮、值使死门都显式给出，九宫逐宫有星门神与天地盘干。解读前先核对这些字段，而不是直接开始讲故事。

**我**：大六壬呢？

**Codex**：输入用日期 + 小时：

```powershell
echo '{"date":"2026-11-03","hour":12,"minute":0,"timezone":"Asia/Shanghai","question":"这次合作的结果"}' | node scripts/taibu.mjs call daliuren -
```

真实输出：

```text
四柱: 丙午 戊戌 辛巳 甲午
课式: 辛巳日第九局 干上未 / 遥克课
月将: 卯
空亡(申,酉) / 驿马(亥) / 丁马(丑) / 天马(戌)

四课: 一课 天后 未/辛；二课 朱雀 辰/未；三课 勾陈 寅/巳；四课 白虎 亥/寅
三传: 初传 寅 勾陈 妻财 戊；中传 亥 白虎 子孙 乙；末传 申 太阴 兄弟 -
```

技能要求先校时、再核实农历转换，然后才出四课三传；这几项都在输出里能逐项核对。

**我**：按这个流程做，最容易卡在哪一步？

**Codex**：最常见的是让模型自己排盘：日柱、卦象一旦算错，后面的解读再顺也没有意义。遇到时先按本节记录的顺序排查，通常都能定位到具体原因。

如果只记住一句，那就是：先让最小链路真实跑通，再谈优化和自动化；跳过验证直接堆功能，最后往往要花更多时间回头补。

### 总结

这一节的内容说起来不少，真正值得带走的是下面几条；把它们串起来看一遍，比单独记某一条更有用。

- 奇门/大六壬是时空决策类术数，输入必须包含具体时间与问题。
- 奇门的可核对字段：四柱、节气与局数、值符值使、九宫星门神、全盘格局。
- 大六壬的可核对字段：四柱、课式、月将、空亡/驿马、四课、三传。
- 真实样例两盘四柱一致为“丙午 戊戌 辛巳 甲午”，说明历法与时间转换来自同一套脚本。
- 先核对盘面字段，再做解读；结构化的意义就是让“时间错了”这类问题在解读前暴露。

## 11.4 西方体系：塔罗与占星

### 简介

`tarot-skill` 提供 78 张完整牌义、6 种牌阵、牌间关系理论，以及一个密码学安全随机源的 Python 抽牌脚本，支持正逆位概率和 `--seed` 复现。它自带安全设计：禁用巴纳姆废话清单、自伤信号处理协议，以及“不做医疗/法律/投资/重大人生决定”的边界。塔罗和占星这类西方体系，同样讲'脚本抽牌、seed 复现'和'缺数据就如实说'这两条纪律。

占星侧通过 `taibu-divination` 或专用占星 Skill 输出星盘事实数据，比如太阳/月亮星座、宫位、相位。

### 调用记录

**我**：塔罗用 `--seed 42` 跑一次三牌阵，记录牌面和正逆位，再用同一 seed 重跑。

**Codex**：抽牌脚本必须运行，不能凭感觉选牌：

```powershell
python scripts/draw.py --spread three --seed 42 --time-factor night --question "这次合作的结果"
```

真实输出：

```json
{
  "seed": 42,
  "spread": "三牌阵",
  "time_factor": "night",
  "cards": [
    {"position": "过去", "card": "圣杯国王", "orientation": "正位", "is_major": false},
    {"position": "现在", "card": "倒吊人", "orientation": "正位", "is_major": true},
    {"position": "未来", "card": "宝剑八", "orientation": "正位", "is_major": false}
  ]
}
```

**我**：重跑结果一样吗？

**Codex**：两次输出 SHA-256 完全一致：

```text
67aaaad96ea0609d8409e345ad727948863d787f98f1ffe1bc8a9524b3843daf  (两次相同)
```

注意 Windows 控制台默认 GBK，直接跑会出现中文乱码；加 `PYTHONUTF8=1` 后输出才是正常中文。`seed` 和 `time_factor` 必须同时给出才能复现，技能也要求输出里展示这两个字段。

**我**：占星呢？

**Codex**：用太卜的 `astrology` 排盘，不提供经纬度时会明确降级：

```text
太阳: 摩羯座 / 10°01
月亮: 天蝎座 / 9°18
上升: 未计算（需经纬度）
天顶: 未计算（需经纬度）
说明: 未提供完整经纬度，已按 0°N, 0°E 近似计算
```

它没有为了“看起来完整”编一个上升星座，这是正确的边界。要得到上升、天顶和宫位，必须提供出生地点/经纬度；`Dasha` 属于吠陀占星体系，不在这个西方占星工具的输出里，不能硬套。

**我**：这一步有没有什么容易被忽略的细节？

**Codex**：最常见的是让模型自己排盘：日柱、卦象一旦算错，后面的解读再顺也没有意义。先别怀疑工具本身，多数情况是环境、路径或前置条件没对上。

本节记录里保留了失败和阻断，不是为了吓人，而是让你知道正常使用中也会遇到这些情况，遇到了照着排查即可，不必怀疑自己。

### 总结

这一节的内容说起来不少，真正值得带走的是下面几条；把它们串起来看一遍，比单独记某一条更有用。

- 塔罗必须先跑 `draw.py`，输出里必须带 `seed` 和 `time_factor` 才能复现。
- 真实样例：seed 42 → 圣杯国王（过去）/ 倒吊人（现在）/ 宝剑八（未来），两次哈希一致。
- Windows 中文输出要加 `PYTHONUTF8=1`，否则控制台乱码。
- 抽牌不做医疗、法律、投资和重大人生决定；遇到自伤表达要暂停占卜并给出求助渠道。
- 占星缺经纬度时，上升/天顶如实“未计算”，不编造；Dasha 不属于西方占星工具的输出。

## 11.5 综合路由：一个 Skill 覆盖多术数时怎么选

### 简介

`metaphysics-synthesis-skill` 覆盖八字、梅花、六爻、风水、塔罗的综合解读；`fortune-telling-skill` 是娱乐导向的命理 Skill，把八字、五行、塔罗、星座、流年与图片/视频取象结合。综合路由的价值在于“先选方法，再排盘”，而不是不声不响地选一个术数开始算。当一个技能覆盖多种术数时，最重要的不是它'会多少'，而是它会不会先问清楚该用哪一套。

`synthesis` 的 Fast Router 给出一张默认路由表，并要求在综合前给每个方法标记 `runnable` / `partial` / `blocked`，只从可运行的方法综合；blocked 的事实不能拿想象填。

### 调用记录

**我**：最近事业有点卡，想看看方向。

**Codex**：这句话太模糊，先不排盘。按 `synthesis` 的路由，必须先分清问题类型：

```text
人生长线 / 十年运势 / 职业倾向 → 八字
突发事件 / 近期动向 / 时机 → 梅花
具体成败 / 合同 / 上司 / 薪资 → 六爻
办公/居家方位与布局 → 风水
心理、关系、选择困境 → 塔罗
```

对“事业卡住、想看方向”，先追问：你要的是**短期决策**（要不要换工作）、**时空择时**（什么时候谈/投/动），还是**命盘结构**（长期适合什么方向）？三种诉求会选不同体系。

**我**：如果三种都想要呢？

**Codex**：`synthesis` 要求拆题：多个不相关目标要拆开分别读。先给每个方法定状态：

```text
八字：runnable（有出生信息）
六爻：runnable（有具体问题和起卦输入）
塔罗：runnable（可抽牌）
风水：blocked（没有平面图/朝向）
```

只有可运行的方法参与综合；blocked 的“风水方位”不能靠想象补。`fortune-telling` 则更强调娱乐框架：先声明这是民俗/自我反思，不把结果说成确定或科学证明。

**我**：专项 Skill 和综合路由有什么区别？

**Codex**：专项 Skill 的入口就是“这件事怎么算”；综合路由的入口是“这件事该用哪套算”。对模糊问题，综合路由会先做方法选择与拆题，专项 Skill 可能直接进入自己的领域。所以“最近事业有点卡”这种话，先交给综合路由更安全。

**我**：如果第一次没跑通，通常先查哪里？

**Codex**：最常见的是让模型自己排盘：日柱、卦象一旦算错，后面的解读再顺也没有意义。把这一步记下来，下次再遇到同类问题时能少走不少弯路。

做完这一节，建议把关键命令和输出随手记在自己的笔记里；下次再遇到同类任务，翻自己的记录通常比重新搜索更快。

### 总结

这一节的内容说起来不少，真正值得带走的是下面几条；把它们串起来看一遍，比单独记某一条更有用。

- 综合路由先选方法再排盘，不允许不声不响地挑一个术数开始算。
- 默认映射：长线看八字、近期看梅花、具体成败看六爻、空间看风水、心理选择看塔罗。
- 多目标问题要拆题；每个方法标记 `runnable/partial/blocked`，只综合可运行的方法。
- 娱乐导向 Skill 要提前声明“民俗/反思”框架，不把结果当确定预测。
- 证据冲突时按层级取主证：直接事实 > 完整结构 > 重复确认 > 近距离具体问题。

## 11.6 边界收束：可复现 + 不越界

### 简介

这一章不引入新 Skill，而是把全章的验收标准收束成两条。第一条是**可复现**：排盘/起卦必须有脚本输出、可核对字段、可重复的结果。第二条是**不越界**：解读层必须自带边界声明——不做医疗、法律、金融等重大决策的替代，遇到自伤信号要暂停占卜并给求助渠道。把全章的规矩收成两条——可复现和不越界——之后，任何命理 Skill 都能拿同一把尺子去量。

`tarot-skill` 的“禁用巴纳姆废话 + 自伤信号处理协议”和 `fortune-telling-skill` 的安全边界，是可直接借鉴的模板。

### 调用记录

**我**：任选一个跑通的命理 Skill，检查它是否同时满足 (a) 有排盘/起卦事实字段，(b) 有显式边界声明或高风险话题处理规则。

**Codex**：用塔罗做检查。事实层：`draw.py` 输出 `seed: 42`、三张牌名、正逆位；这些是 (a)。边界层：`SKILL.md` 明确写了：

```text
不做医疗、法律、投资买卖、重大人生决定；
明确自伤表达时暂停占卜，建议联系当地紧急服务/可信任的人，
或中国心理援助热线 400-161-9995。
反巴纳姆：建议必须具体到时间/动作，避免“注意沟通、保持平衡、相信直觉”。
```

这些是 (b)。同时它还要求“主权归用户”：不用“你一定会”，结尾提醒“牌显示的是当下能量，你的选择随时可以改变走向”。

**我**：只有 (a) 没有 (b) 会怎样？

**Codex**：那是“算得准但不敢用”。比如排盘很完整，但把结论说成“你一定会离婚/一定会破财”，就跨过了决策边界。`fortune-telling` 的原则也写得很清楚：never present outcomes as certain、never replace medical/legal/financial/safety advice。

**我**：只有 (b) 没有 (a) 呢？

**Codex**：那是“话说得漂亮但不可验证”。比如只说“相信直觉、保持平衡”，没有盘面字段、没有 seed、没有脚本输出，你无法核对也无法复现。

**我**：那八字/六爻这侧怎么验收？

**Codex**：同样两条。八字看 `chart.json` 的四柱、日主、命宫、大运是否由 `run-chart.js` 产出；六爻看 `numbers` 与两次哈希是否一致；奇门看局数/值符值使/九宫是否显式；大六壬看四课三传是否完整。解读再怎么写，都要回到这些字段上引用。

**我**：按这个流程做，最容易卡在哪一步？

**Codex**：最常见的是让模型自己排盘：日柱、卦象一旦算错，后面的解读再顺也没有意义。遇到时先按本节记录的顺序排查，通常都能定位到具体原因。

把这一节放回整条链路里看，它只是其中一段；真正动手时不必追求一次全对，先把命令跑通、把输出对上，遇到报错再回来查对应位置，往往比从头读一遍更快。

### 总结

这一节的内容说起来不少，真正值得带走的是下面几条；把它们串起来看一遍，比单独记某一条更有用。

- 验收两条：事实字段可核对、结果可复现；解读自带边界声明。
- 只有事实没有边界，是“算得准但不敢用”；只有边界没有事实，是“好听但不可验证”。
- 塔罗的 `seed`/`time_factor` 与八字/六爻的脚本输出是可复现证据。
- 高风险话题必须交给专业渠道；自伤信号要暂停占卜并给出求助方式。
- 主权归用户：牌面和盘面描述“当下能量”，不是不可改变的宿命判决。
